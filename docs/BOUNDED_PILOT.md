# Ограниченный пилот и стратегия ежедневных изменений

Pilot.gs подготовлен для будущего ручного запуска владельцем. В этом PR
не выполнялись ни загрузка в Apps Script, ни запуск пилота, ни массовый сбор.

## Почему нельзя продолжать полный обход

Реальный totalCount=32 440 437 означает 324 405 запросов по 100 либо
162 203 по 200 без повторов. [Квота URL Fetch](https://developers.google.com/apps-script/guides/services/quotas)
обычно 20 000/сутки consumer или 100 000 Workspace. Полный ежедневный scan
не укладывается даже в Workspace. Квоты разделяются с другими скриптами
пользователя, поэтому локальный счётчик не является остатком квоты Google.

## Четыре проверяемых потока

Используются реальные документированные поля:
[LotsFiltersInput](https://ows.goszakup.gov.kz/help/v3/schema/lotsfiltersinput.doc.html),
[TrdBuyFiltersInput](https://ows.goszakup.gov.kz/help/v3/schema/trdbuyfiltersinput.doc.html),
[официальное описание диапазонов](https://old.goszakup.gov.kz/ru/developer/ows_v3).
`[from,to]` — документированная форма; точная зона, включительность границ,
задержка индексации и все причины изменения ещё требуют реальной проверки.

| Поток | Ограниченная выборка | Зачем |
| --- | --- | --- |
| Новые публикации | TrdBuy.publishDate, затем Lots.trdBuyId по полученным ID | Публикация хранится в объявлении, одного роста ID лотов недостаточно |
| Изменения лотов | Lots.lastUpdateDate | Статус, сумма, удаление и другие изменения старых лотов |
| Изменения объявлений | TrdBuy.lastUpdateDate, затем Lots.trdBuyId | Сроки/публикация могут измениться без обновления Lots |
| Поздняя индексация | Lots.indexDate | Дополнительный поиск поздно попавших в индекс записей |

Нет предварительного фильтра по статусу, товарности, цене или isDeleted.
Все способы сохраняются раздельно: плановый/фактический — разные поля.
Дедупликация пересечений — Lots.id; данные позднего ответа обновляют
наблюдение. Несогласованные ответы одного ID в одном запуске дают
sourceChangedDuringRun и complete=false; это не атомарный снимок реестра.

На каждом запросе проверяются pageInfo, монотонность/уникальность ID,
продвижение lastId, неизменность filtered totalCount и равенство количества
прочитанных записей totalCount при hasNextPage=false. У дочерней выборки
проверяется trdBuyId, у диапазонной — принадлежность даты окну. Короткая
страница не считается концом. Пустая промежуточная страница с hasNextPage
даёт ошибку: пилот не утверждает её полноту. Если API возвращает глобальный
или нестабильный totalCount, пилот остановится, а контракт нужно уточнить.
Наличие этих проверок не обнаруживает запись, которую API совсем не вернул;
нужна независимая контрольная выборка ожидаемых ID.

## Что реализовано в пилоте

- Только runTenderBoundedPilot вручную, с подтверждённой конфигурацией и
  свежим proof testGoszakupV3Connection. Три обязательных свойства не угадываются.
- TENDER_PILOT_WINDOW — JSON `{ "from": "YYYY-MM-DD HH:mm:ss", "to": "YYYY-MM-DD HH:mm:ss" }`
  в подтверждённой зоне источника. Прошедшее окно, длина >0 и ≤1 часа.
  Это форма ввода, не готовое значение для вставки; выберите реальные даты.
- Страница 20; максимум 40 HTTP-попыток за запуск, включая retries; 200
  попыток за скользящие 24 часа, 200 уникальных Lots.id, 100 ID планов.
  Перед каждой попыткой резервируется запись TENDER_PILOT_QUOTA.
- Проверка длительности 120 секунд перед очередным HTTP; уже выполняемый
  UrlFetch нельзя прервать этим таймером. Google имеет собственный лимит
  исполнения. Продолжения/автоматические повторные запуски не создаются.
- Максимум 2000 записей в каждом пилотном листе; при достижении лимита
  остановка без автоматического удаления истории. Локальные лимиты
  консервативны, но не заменяют проверку остальных расходов пользователя.
- Собственные четыре листа создаются только при явно запущенном пилоте;
  несовместимые заголовки останавливают работу. Основные ALL_LOTS,
  NEW_TODAY, ACTIVE_LOTS и существующее состояние синхронизации не меняются.

| Лист | Данные |
| --- | --- |
| PILOT_LOTS | Один снимок на Lots.id, классификация, статус, исходная публикация, плановый/фактический способы, JSON нормализованного товара только при подтверждении |
| PILOT_EVENTS | NEW_PUBLICATION, FIRST_OBSERVED, STATUS_CHANGED, LOT_UPDATED с уникальным ключом ID/предыдущая ревизия/новый hash |
| PILOT_QUARANTINE | Неподтверждённые типы/планы или дефекты нормализации, причина по ID |
| PILOT_RUNS | Потоки, страницы, totals, расходы, полнота, ошибки и карантин |

NEW_PUBLICATION означает **впервые наблюдённый в пилоте** ID с датой
публикации внутри выбранного окна. Первый обнаруженный старый лот —
FIRST_OBSERVED. Перемена статуса известного ID — STATUS_CHANGED, другое
изменение — LOT_UPDATED. Это события наблюдений, не журнал всех переходов:
статус мог смениться несколько раз между опросами. Изменение статуса имеет
приоритет, если одновременно менялась сумма. Класс события явный:
событие публикации QUARANTINE не является новым подтверждённым товаром.

События записываются и flush выполняется до снимков. Повтор после сбоя
использует тот же event key; нормальный следующий переход имеет новую
ревизию и не теряется. Исчезновение из запроса не удаляет снимок. Планы
запрашиваются по явному pointList; подробнее [правила](STAGE2_READINESS.md).
Секреты/Authorization/сырые ошибки не экспортируются. Внешние строки
защищены от формул, отражённый токен очищается до записи.

При лимите/ошибке остаются ограниченные полученные наблюдения и отчёт
complete=false. Частичный результат не продвигает прогресс. **Ни один
пилот не сохраняет ежедневный watermark**, даже успешный. Повторное окно
читается сначала, с дедупликацией событий. complete=true означает лишь
завершение четырёх фильтрованных выборок для этого окна без замеченных
нарушений; quarantineCount надо оценивать отдельно. countryCoverageVerified,
dailyCoverageVerified, watermarkAdvanced и mvpReady всегда false в отчёте
пилота. Статус базового адаптера можно посмотреть отдельно getTenderStatus.

## Проверка владельцем после отдельного разрешения

1. Получить официальный ответ о зоне/датах (вопросы в STAGE2_READINESS.md).
   Не задавать предполагаемую зону, не переносить её из манифеста.
2. Рассмотреть PR; отдельно разрешить безопасную загрузку восьми .gs через
   существующие prepare/publish проверки. Этот PR не запускает workflow.
3. После подтверждения зоны, шаблона и выбранного набора статусов настроить
   свойства в Google, выполнить testGoszakupV3Connection/getTenderStatus.
   Нужны свежий proof и mvpReady=true. Токен остаётся на месте.
   Если первые страницы содержат только удалённые проекты, дополнительно
   задайте GOSZAKUP_DIAGNOSTIC_LOT_IDS = `[43495954]`: диагностика выполнит
   ещё один точечный запрос и проверит нормализацию известного товара.
   Это не отменяет ошибки других образцов или проверку двух страниц. Если
   известный лот уже изменён/удалён, proof без подходящего образца не выдаётся.
4. Выбрать небольшое прошедшее окно с заранее известными контрольными ID.
   Отдельно разрешить его запуск; затем ввести TENDER_PILOT_WINDOW и вручную
   выполнить только runTenderBoundedPilot.
5. Прислать очищенный отчёт PILOT_RUNS, причины карантина, контрольные ID
   и их сырые даты/статусы. Токены, ключи и заголовки присылать не нужно.
6. Сопоставить: все ожидаемые ID в снимках; публикации отдельно от смен
   статуса; plan fallback сопоставлен с pointList; нет дубликатов; сумма
   ≤10 млн взята из Lots; при повторном окне нет лишних событий.
7. Проверить окна по обе стороны границы, повтор после задержки индекса,
   известное обновление старого лота/TrdBuy и удаление. Сделать несколько
   контрольных выборок разных способов/периодов, а не только две страницы.
8. Если окно плотное или лимит достигнут — согласовать меньшие окна;
   не повышать жёсткие лимиты автоматически. Не запускать sync/trigger.

## Будущий ежедневный режим: проект решения, ещё не реализован

После пилота нужны четыре независимых watermark и фиксированные окна с
сохраняемыми курсорами/очередью дочерних ID. Продвигать границу только
после всех страниц, записи/flush событий и снимков, проверки контрольных
ID и принятого решения по карантину. При квоте/сбое продолжать то же окно;
плотные окна делить, никогда не объявлять частичную выборку завершённой.

Размер перекрытия предыдущих окон и задержку закрытия нового окна выбрать
по фактической задержке индексатора, а не произвольным 24 часам.
Дедупликация позволяет безопасно перечитывать границы. Повторно проверять
известные активные/карантинные Lots.id отдельными ограниченными пакетами,
чтобы видеть изменения связей и сроков; сверять с независимыми контрольными
ID. Документированный журнал изменений, если API подтвердит его полноту,
может заменить часть потоков; существование/контракт такого endpoint
здесь не утверждается. Без гарантии обновления дат при изменении Plans
ни четыре потока, ни опрос только активных ID не доказывают все изменения.

Сначала измерить суточные объёмы, запросы/лот, задержку, время Sheets/HTTP,
квоты и размер хранения. Для длительного хранения нужны периодные листы/
таблицы, пакетная запись и проверяемые архивы, чтобы не достигнуть лимита
Sheets 10 млн ячеек. Это возможно на Apps Script + Sheets, без сервера,
но архивирование и production-курсор в этом PR не внедрены. Требование
«все новые ежедневно» остаётся непроверенным до успешного реального
пилота и определения гарантий источника.
