использовать как ID: в примере аукциона номер 13537270-2, ID 13633135.

Официальная [схема Lots](https://ows.goszakup.gov.kz/help/v3/schema/lots.doc.html)
описывает **refTradeMethodsId как код планового способа**, а
**refBuyTradeMethodsId как код фактического способа**. Расхождение 3/6
у одного источника не исправляем и не объединяем. В пилоте отдельные
колонки PLANNED_METHOD_ID и ACTUAL_METHOD_ID. Суффикс номера лота и
поле способа объявления не заменяют фактический способ Lots. Смысл
конкретных числовых кодов сверяют со справочником способов; этот PR
не назначает по ним право подачи и не выбирает другой URL.

## Пустые Plans: неизвестный тип

В пробе **11/20** лотов не имеют Plans. Их нельзя считать товарными по
названию, цене, типу объявления, суффиксу номера или соседним записям.

Пилот использует документированный
[Query.Plans](https://ows.goszakup.gov.kz/help/v3/schema/query.doc.html)
с [PlansFiltersInput.id](https://ows.goszakup.gov.kz/help/v3/schema/plansfiltersinput.doc.html)
для недостающих **явных** pointList ID. Получает только `id refSubjectTypeId`;
сумму/количество плана не запрашивает. Допускается максимум 100 ID
планов на запуск. Не вернувшиеся ID и избыток этого лимита остаются
неподтверждёнными. Эта возможность документирована, но ещё не испытана
в реальном аккаунте; наличие поля в схеме не гарантирует заполнение связи.

Только полный, непротиворечивый набор планов всех pointList с типом 1
разрешает классификацию ELIGIBLE_GOODS, при Lots.amount ≤10 млн.
Пустые pointList, отсутствующие/неполные Plans, неизвестный тип,
повторы/конфликты планов или некорректные данные — PILOT_QUARANTINE.
Ни одна такая запись не попадает в ALL_LOTS или товарный результат.
Предыдущая версия остаётся наблюдением с текущим классом QUARANTINE,
не сохраняется как якобы актуальный подтверждённый товар.

isDeleted=1 исключается до проверки связей, isDeleted=0 проверяется
полностью, другие значения не интерпретируются. Фильтра isDeleted нет
ни в опубликованном LotsFiltersInput, ни в пользовательском introspection.
Пилот фильтрует даты, затем проверяет удаление локально; не скрывает
завершённые, дорогие или нетоварные записи входным фильтром — их изменение
может исключить ранее известный товар. Пропажа ID из выдачи не равна удалению.

## Временная зона: блокер сохраняется

Повторно прочитаны официальные developer/ows_v3, Lots и TrdBuyFiltersInput.
Документация подтверждает поля и диапазоны дат, но в этих источниках
не найдено указание IANA timezone/offset строк API. Зона манифеста и
текущее гражданское время Казахстана не устанавливают правила сервиса.

Нужен официальный ответ владельца API или спецификация, устанавливающие:

1. В какой IANA-зоне или фиксированном UTC offset возвращаются строки
   без смещения publishDate/startDate/endDate/lastUpdateDate/indexDate?
2. Как хранятся/возвращаются даты до и после изменения времени 01.03.2024?
   Старая строка переинтерпретирована или сохраняет историческое смещение?
3. В какой зоне интерпретируются границы фильтров, включительны ли они,
   какова задержка индексации и точность времени?
4. Отмечают ли изменения статуса/связей/удаления Lots и изменения TrdBuy
   lastUpdateDate и indexDate? Возможны ли изменения Plans без обновления Lots?

Запрос поддержке здесь подготовлен, но не отправлен. Если сервис отдаст
ISO-дату с Z/offset, конкретный момент уже однозначен; это не доказывает
зону остальных строк без offset. **GOSZAKUP_API_DATE_TIMEZONE оставить
незаполненным до официального подтверждения**, mvpReady=false сохраняется.

| Свойство | Что можно утверждать |

| GOSZAKUP_ACTIVE_STATUS_CODES | Консервативные кандидаты `["PublishedBidAccept","PublishedOfferAccept"]`, не доказан полный набор и доступность поставщику |

[Все 37 статусов](stage2/status-reference.user.json) и
[их разбор](stage2/STATUS_REVIEW.md) уже сохранены. 230 — дополнения,
245 — проверка после подачи, 210 — публикация без гарантии начала подачи.
Статус плюс открытый срок дают наблюдаемую активность, но не отменяют
условий способа и приглашений. Значения свойств автоматически не меняются.

Владелец уже выполнил inspectTenderStage2Evidence в Google. Новый Pilot.gs
пока есть только в репозитории. Порядок дальнейших действий:

1. Рассмотреть этот PR и получить официальное подтверждение зоны/фильтров.
2. Отдельно разрешить публикацию новой версии через prepare → проверка → publish.
3. После подтверждения настроек повторить testGoszakupV3Connection;
   сохранить свежую проверку конфигурации, убедиться в mvpReady=true.
   Для дополнительного подходящего образца можно задать
   GOSZAKUP_DIAGNOSTIC_LOT_IDS = `[43495954]` (не более пяти явных ID);
   удалённые проекты из начальных страниц не заменят реальный товар.
4. По [инструкции ограниченного пилота](BOUNDED_PILOT.md) выбрать прошедшее
   окно ≤1 часа и отдельно разрешить его запуск. Здесь он не запускался.
5. Сверить ожидаемые API/портальные записи, границы, обновления и карантин;
   только затем проектировать разрешённый ежедневный режим.

**syncTenderLots, dailyTenderSync/продолжения и installDailyTrigger в новом
коде блокируются даже при mvpReady=true**. Это готовность базового адаптера,
а не подтверждение безопасного ежедневного охвата. Триггеры не удаляются
этим PR; существующий автоматический запуск, если он есть, остановится
на проверке до HTTP/записи/планирования продолжения после публикации.


## Решение владельца по отображению времени (2026-10-09)
Владелец подтвердил: **пользовательский интерфейс, Google Sheets и расписания должны показывать время Казахстана UTC+05:00**. Это требование к отображению и расписанию, а **не** официальный ответ о временной зоне строк OWS v3 без offset. Исходные строки API сохраняются без преобразования; GOSZAKUP_API_DATE_TIMEZONE не заполнять на основании одного этого решения. Блокер #6 для реального date-window пилота остаётся до подтверждения семантики источника.
