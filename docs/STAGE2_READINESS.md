## Документированные фильтры и нормализация

[LotsFiltersInput](https://ows.goszakup.gov.kz/help/v3/schema/lotsfiltersinput.doc.html)
содержит `id: [Int]`, `lotNumber: String`, `refLotStatusId: [Int]`.
**Фильтра isDeleted в опубликованном input нет.** `Lots.isDeleted` — поле
результата. Диагностика также проверяет фактический input через introspection,
но не применяет недокументированный фильтр даже если сервис его добавил.

Для проверки одного известного лота используются отдельно `id:[43495954]`
и `lotNumber:"88105345-ЗЦП1"`. Для исследования заполненных связей допустима
ограниченная выборка по известным опубликованным статусам `[210,220,230,240]`.
Этот исследовательский фильтр не является фильтром всех новых лотов или
полным перечнем разрешающих подачу статусов. Планы и даты выбираются
явно: `Plans { id refSubjectTypeId }`, `TrdBuy { publishDate startDate endDate ... }`.

Текущие проверки сохраняются: isDeleted=1 исключается; isDeleted=0
требует полного покрытия pointList планами; все типы предмета должны быть
1 (товар). Пустой Plans у живого лота вызывает ошибку, а не пропуск.
Количество/сумма берутся только из Lots, лимит ≤10 000 000 включительный.
Даты без смещения не интерпретируются до подтверждения зоны источника.

### Статусы: известные коды и ограничения

Пользователь передал полный справочник из 37 записей (`complete=true`).
Сохранены [реальный отчёт](stage2/status-reference.user.json) и
[разбор всех 37 состояний](stage2/STATUS_REVIEW.md). Имена и коды не
угадываются: в отчёте 37 уникальных ID, 36 code; ID 295 и 300 имеют один code.

| Реальный код / ID из пользовательского отчёта | Что подтверждено | Ограничение |
| --- | --- | --- |
| PublishedOfferAccept / 240 | Приём ценовых предложений; также пример официальной документации | Нужен открытый интервал подачи |
| PublishedBidAccept / 220 | Приём заявок | Доступность конкретному поставщику зависит от способа и условий |
| PublishedBidAdditional / 230 | Дополнение заявок | Не доказывает возможность подачи новой первоначальной заявки |
| Published / 210 | Опубликован | Не означает, что приём уже начался; публичные примеры ОК/РБС имеют будущий startDate |
| PublishedBidVerification / 245 | Проверка заявок | По официальным инструкциям ОК/аукциона начинается после завершения приёма, исключён из новых заявок |

[Инструкция ЗЦП](https://wiki.goszakup.gov.kz/pages/viewpage.action?pageId=1311154)
требует статус приёма ценовых предложений;
[инструкция ОК](https://wiki.goszakup.gov.kz/pages/viewpage.action?pageId=1311120)
требует начало интервала и статус приёма заявок.
[Инструкция аукциона](https://wiki.goszakup.gov.kz/pages/viewpage.action?pageId=1311047)
отделяет подачу заявок от ожидания и проведения торгов: ожидание аукциона
не означает возможность новой заявки.
[Инструкция из одного источника](https://wiki.goszakup.gov.kz/pages/viewpage.action?pageId=1311082)
указывает подачу после приглашения. Поэтому ACTIVE_LOTS не гарантирует
право конкретного пользователя участвовать. Нельзя угадывать остальные
коды по именам или применять статус объявления как код статуса лота.

### Временная зона

В просмотренных официальных API-страницах источник временной зоны строк
TrdBuy без смещения не указан. Подтверждены только строки времени портала.
Нужны реальные publishDate/startDate/endDate этого же объявления из API
и сравнение с тремя приведёнными значениями. Если API возвращает ISO-дату
с Z/offset, сам offset даёт момент времени. Если строка без offset совпадает
с порталом, это подтверждает совпадение представлений на этом примере,
но ещё не политику исторических дат. Зону и правила старых записей нужно
подтвердить официальным описанием или ответом поддержки Goszakup.

## Диагностика для запуска владельцем

В PR подготовлена функция **inspectTenderStage2Evidence** в Diagnostics.gs.
Она выполняет четыре ограниченных GraphQL-запроса: introspection input,
пять известных ID, независимый поиск первого номера и максимум 20 записей
по четырём известным опубликованным статусам. Она возвращает выбранные
поля, состояние Plans/TrdBuy, исходные даты и результат сверки ID.

Функция не пишет Sheets, Script Properties, курсор или proof готовности,
не создаёт триггеры и не запускает сбор. Ответы очищаются от токена до
ограничения строк; произвольные поля/тела ошибок не экспортируются.
Длинный JSON выводится нумерованными частями STAGE2_JSON_PART_N.
Соедините содержимое частей после двоеточия по порядку.

**Функция ещё не загружена в Google.** Сначала проверить/объединить PR;
её публикация через существующий безопасный prepare/publish процесс
требует отдельного подтверждения владельца. После разрешённой публикации
запустить только inspectTenderStage2Evidence и передать её отчёт без токена.
Полный справочник статусов уже получен и сохранён; повторять его экспорт
нужно только при изменении справочника или появлении неизвестного кода.
Наличие функции в GitHub не означает её наличие в Apps Script.

## Масштаб и следующие действия

По полученному totalCount текущий полный обход потребует 324 405 страниц
по 100 записей или минимум 162 203 по 200. Официальные
[квоты URL Fetch Apps Script](https://developers.google.com/apps-script/guides/services/quotas):
20 000 в сутки для consumer, 100 000 для Workspace. Повторы и другие
запросы только увеличат расход. Полный ежедневный scan такого реестра
не укладывается даже в стандартную квоту Workspace.

До боевого сбора нужны проверенная стратегия по датам изменений/публикаций,
замер квот и объёма Sheets, сверка обновлений/удалений и период первого
сбора. Текущая полная пагинация не решает задачу ежедневного охвата этого
масштаба. `mvpReady=true` в диагностике не является доказательством
полного ежедневного охвата и не снимает этот блокер.

Порядок: получить точечный API-отчёт → проверить полный справочник и зону →
подтвердить конфигурацию → повторить testGoszakupV3Connection/getTenderStatus →
подготовить ограниченный первый сбор и стратегию ежедневных изменений.
До подтверждения готовности и плана сбора **не запускать syncTenderLots
и installDailyTrigger**. Этот PR не меняет production-фильтры, нормализацию,
проверки готовности или workflow безопасности.
